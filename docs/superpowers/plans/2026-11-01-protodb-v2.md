# ProtoDB 2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild ProtoDB's internals so that every collection is indexable, commits are durable and serializable per root, queries equal full scans, and everything is proven on Python 3.14t.

**Architecture:** Bottom-up rebuild under the existing concepts: value model → atoms/codec → storage v2 → collections with a shared index plumbing → index framework → transactions → query planner/LINQ → vectors → peripherals → benchmarks → docs. Each phase is green and committed before the next starts.

**Tech Stack:** Python ≥ 3.11 (primary test target 3.14t free-threaded), msgpack, psutil, numpy (vectors extra), optional hnswlib, pytest, hypothesis, pytest-timeout, pytest-cov, Sphinx.

**Spec:** `docs/superpowers/specs/2026-11-01-protodb-v2-design.md` (read it first; section numbers below refer to it).

## Review Focus

1. Concurrent commits from many threads on 3.14t on the same root — expect no lost update and no deadlock (Task 5.2 stress test).
2. Process killed between segment fsync and root rename, or mid-record — expect reopen to the last published root (Task 2.3 crash matrix).
3. Mixed-type keys (`True`, `1`, `1.0`, `Decimal("1")`, `10**16+1`, `None`, missing attribute) in indexed queries — expect index result == scan result (Task 6.3 property).
4. Mutating an indexed collection through every mutator, then committing and reloading — expect indexes present and consistent (Task 4.4 contract).
5. Large structures (10^5 elements) — expect no recursion error and O(log n) behaviour (Task 3.1 property + Task 9 benchmark).
