# ProtoDB 2.0 decision log

ADR-style entries. Each records context, decision, alternatives and consequences.
Source: `docs/superpowers/specs/2026-11-01-protodb-v2-design.md` section 2.

## D1 - Full repair of the internals
- Context: the 0.1 internals have structural defects (identity, durability, ordering, conflicts).
- Decision: rebuild the internals module by module under the existing concepts.
- Alternatives: patch incrementally; rewrite with a new API.
- Consequences: public concepts survive; 0.1 modules are removed at once in Task 8.5.

## D2 - One value model with a total order
- Context: index scans and collection scans compared values differently.
- Decision: a single total order across types (spec section 4), shared by indexes and scans.
- Alternatives: per-index comparators; Python's native ordering.
- Consequences: heterogeneous values are comparable; the comparator is a core module.

## D3 - Canonical types
- Context: serialization needs a closed set of values.
- Decision: `None, bool, int, float, Decimal, str, bytes, date, time, datetime (naive or aware), timedelta, UUID, tuple, list, dict`, plus atoms.
- Alternatives: pickle-like arbitrary objects.
- Consequences: safe, portable encoding; other types must be converted by the caller.

## D4 - On-disk format v2
- Context: the 0.1 format has no integrity checks.
- Decision: framed binary records, msgpack payloads, CRC32, per-segment header. A `protodb inspect` CLI replaces human-readable files. Parquet is an export format only.
- Alternatives: keep JSON-like files; Parquet as the store.
- Consequences: corruption is detectable; inspection needs tooling.

## D5 - Cloud and cluster coordination
- Context: UDP voting is unreliable.
- Decision: CAS on the root via conditional writes; data written strictly before the root; UDP voting removed.
- Alternatives: keep voting; external lock service.
- Consequences: relies on providers offering conditional writes.

## D6 - Durability
- Context: commits were not durable.
- Decision: fsync per commit by default; `durability="flush"` and `"none"` are explicit opt-outs for tests and benchmarks.
- Alternatives: no fsync; group commit now.
- Consequences: safe by default; group commit is a later optimisation.

## D7 - Strings stored inline
- Context: the global `Literal` catalog added indirection and contention.
- Decision: strings are stored inline; the catalog is removed; reading a string returns `str`.
- Alternatives: keep the catalog with caching.
- Consequences: simpler reads; repeated strings are not deduplicated.

## D8 - Dictionary as key-ordered persistent AVL tree
- Context: binary search over a positional list gave O(log^2 n).
- Decision: `Dictionary` is a key-ordered persistent AVL tree, O(log n).
- Alternatives: HAMT; keep the positional list.
- Consequences: ordered iteration and range queries; structural sharing on update.

## D9 - Conflict implies retry
- Context: lost updates under concurrency.
- Decision: conflict raises and the caller retries. Read sets include absent roots. `ConcurrentOptimized` merge (per-key/per-element op-log replay) applies only to roots the transaction did not read.
- Alternatives: last-writer-wins; always merge.
- Consequences: serializable behaviour; merge is a controlled optimisation.

## D10 - Atom identity
- Context: equality used `id()` or storage pointers, which change.
- Decision: every atom gets a stable `oid` (UUID4) at creation, persisted; equality and hashing use `oid`.
- Alternatives: pointer identity; content hashing.
- Consequences: stable identity across saves; 16 extra bytes per atom.
- Amended by D21: identity semantics unchanged; the `oid` is assigned lazily, on first need, instead of at construction.

## D11 - MutableObject semantics
- Context: `MutableObject` had undefined concurrency behaviour.
- Decision: keep it as a named mutable cell with read-set conflict detection.
- Alternatives: remove it.
- Consequences: a supported escape hatch for mutable state with defined conflicts.

## D12 - Single exception hierarchy
- Context: several overlapping exception families.
- Decision: one hierarchy rooted at `ProtoDBError`; `ProtoBaseException` remains an alias for one release.
- Alternatives: keep the families.
- Consequences: callers catch one root; old names keep working via aliases in `proto_db.errors`.

## D13 - Optional hnswlib
- Context: `hnswlib` re-enables the GIL on 3.14t.
- Decision: import it lazily and optionally. Default vector backend is exact numpy search; IVF-Flat is persistent and built in.
- Alternatives: hard dependency.
- Consequences: free-threading preserved by default; ANN is opt-in.

## D14 - Python floor and dependencies
- Context: wide compatibility wanted; some dependencies unused.
- Decision: floor stays 3.11; CI matrix 3.11-3.14 plus 3.14t; drop `six` and `wrapt`.
- Alternatives: raise the floor.
- Consequences: no 3.12+ only syntax in the code base.

## D15 - Subpackage layout
- Context: a flat package hid structure.
- Decision: split into subpackages (spec section 3); top-level `proto_db` re-exports the public API.
- Alternatives: stay flat.
- Consequences: clearer ownership; import paths change for internals.

## D16 - Static checker for hygiene
- Context: swallowed exceptions hid failures; test-aware code skewed behaviour.
- Decision: a static checker test forbids swallowed exceptions and test-aware code in `proto_db/`.
- Alternatives: code review only; linters.
- Consequences: `tests/static/` enforces it; scope grows via `CHECKED_ROOTS` until Phase 11 covers the whole package.

## D17 - Value model details
- Context: spec section 4 left list/dict and naive-vs-aware `time` open.
- Decision: rank order is MISSING < None < bool < number < str < bytes < date < time-naive < time-aware < datetime-naive < datetime-aware < timedelta < UUID < tuple < atom. `list` and `dict` are storable (`canonical` accepts them recursively) but are not orderable keys (`order_key` raises `ProtoValidationError`). Aware `time` orders by its UTC-normalised time of day; aware `datetime` orders by UTC microseconds computed from the fold-resolved offset (never by raw aware comparison, which is fold-sensitive).
- Alternatives: order lists/dicts; compare naive and aware times as one rank.
- Consequences: keys and index terms are limited to scalars, tuples and atoms; equal instants in different time zones are equal keys.

## D18 - Atom persistence details and DBObject versions
- Context: spec section 5 left open how a new version of an immutable record is identified, how an absent attribute differs from `None`, and how atoms reach storage before transactions exist (ruling R3).
- Decision: `DBObject.with_(**changes)` returns a new atom with a new `oid`: versions are distinct atoms and compare unequal (D10). An absent attribute reads as `None`; an explicit `None` is stored and `has_defined_attr` tells them apart. Atoms hold a `context` (`PersistenceContext`: `storage`, `save(atom)`, `load(ptr, type_name)`); the saved payload is `{"t": type_name, "oid": 16 bytes, "s": encoded_state}`. References encode as `{"@ref": [segment_hex, offset, type_name]}`. Dicts encode as ordered `[key, value]` pairs (keys may be any canonical value); `tzinfo` is limited to `datetime.timezone` and keyed `zoneinfo.ZoneInfo`. A stub learns its `oid` only when loaded, so `oid`, equality and hashing load a stub.
- Alternatives: keep the `oid` across versions (identity of an entity rather than of a value); encode `None` as absence; persist arbitrary `tzinfo` objects by pickling.
- Consequences: references always point at one exact version; entity identity across versions is an application-level key or a `MutableObject` (D11). Persisted attribute names must not shadow class attributes (methods, properties, class-level defaults), which would bypass lazy loading: saving such state raises `ProtoValidationError`, loading it raises `ProtoCorruptionError`, and DBObject rejects such field names at construction. Integers outside the msgpack range are encoded as signed hexadecimal text, which the int/str digit limit does not cover.

## D19 - FileStorage durability, failure and locking details
- Context: spec sections 6-7 fix the format, the commit pipeline and the root lock, but leave open what each durability mode syncs, what happens after an I/O failure, how `publish_root` relates to `root_lock`, and what to do with a leftover `space.root.tmp`.
- Decision: `"fsync"` syncs segment data, the directory after creating a segment, the temporary root file and the directory after the rename; `"flush"` hands segment data to the OS without fsync but keeps the root fsyncs (process-crash safe, not power-loss safe); `"none"` syncs nothing. Any `OSError` on the write path raises `ProtoUnexpectedError` and marks the instance failed: later pushes, flushes and publishes raise `ProtoUnexpectedError` (reads still work), so no later root can reference records whose write was lost; recovery is opening a new instance. After a failure in the root rename or the final directory fsync the outcome of that publish is unknown until reopen. `publish_root` flushes, verifies that the pointer names a readable record (a root that would make the space unopenable is refused with `ProtoCorruptionError`), then does the epoch CAS and the root replace under the root lock, taking it itself unless the calling thread already holds it. The OS lock is `flock`/`msvcrt.locking` on `space.lock`, opened per acquisition. A leftover `space.root.tmp` is ignored, never deleted at open, because another process may be writing it under the lock. `read_root` reads `space.root` from disk on every call so it sees other processes' publishes.
- Alternatives: retry fsync after a failure (unsafe: the kernel may have dropped the dirty pages); keep writing to a new segment after a failure; a separate lock file for the CAS; removing the tmp file at open.
- Consequences: a failed disk write costs reopening the storage instance. The crash matrix (`tests/crash/test_crash_matrix.py`) checks every write/fsync/rename/directory-fsync point under process-crash, ordered power-loss and metadata-reordering power-loss models.

## D20 - Persistent AVL machinery details
- Context: spec section 8.2 and D8 fix the structure (positional and key-ordered persistent AVL trees) but not the node layout, the error behaviour of positional operations, range-bound conventions or how slices are computed.
- Decision: `proto_db/collections/avl.py` has two atom node kinds, `PosNode` (`value, left, right, height, count`; type name `proto_db.avl.PosNode`) and `KeyNode` (`key, value, left, right, height, count`; `proto_db.avl.KeyNode`); the empty tree is `None`. Fields are set only by constructors (`__setattr__` raises `ProtoUserError`); a `KeyNode` caches `order_key(key)` in a runtime-only attribute. All operations are pure module functions with path copying. Positional indexes must be `int` (not `bool`) within `0..count-1` (`0..count` for insert, `0 <= start <= stop <= count` for slices); anything else raises `ProtoValidationError` - negative-index translation belongs to `List`. `pos_slice` and `pos_concat` use split/join (Blelloch et al., "Just Join") and run in O(log n). `key_put` returns `(root, replaced, old_value)` and keeps the existing key object on replace, as `dict` does; `key_remove` returns `(root, removed, old_value)` and the same root when the key is absent. In `key_iter_range(root, lo=UNBOUNDED, hi=UNBOUNDED, lo_inc=True, hi_inc=True)` only the exported `UNBOUNDED` sentinel leaves a side open; `None` and `MISSING` are ordinary bounds compared by `order_key` (so `lo=None, lo_inc=False` excludes `MISSING` and `None` keys, which `RangeIndex` needs). `key_from_sorted` requires strictly increasing order keys. Traversals and `check_invariants` use explicit stacks; recursive helpers recurse only along one root-to-leaf path. `check_invariants` reports a root height outside 1..128, or any path longer than the root height (cycles), as `ProtoCorruptionError`; a subtree shared by two parents is checked once per path.
- Alternatives: a single node class with a mode flag; an O(k) slice by iteration; `None` as the unbounded marker (rejected: it made ranges bounded at `None` inexpressible and silently wrong); negative indexes in the machinery.
- Consequences: every key value, `None` and `MISSING` included, is usable as a range bound; values are stored unvalidated, so collections call `values.canonical` before inserting; equal keys of different types (`1`, `1.0`) are one key.

## D21 - Lazy atom identity and striped atom locks (amends D10)
- Context: building an atom cost about 4.3 us on 3.14t, of which `uuid.uuid4()` was about 2.1 us and the per-atom `RLock` about 0.2 us. Every persistent collection and index path-copies O(log n) atoms per mutation, and most of those nodes are never saved nor compared, so the cost multiplied everywhere.
- Decision: identity semantics of D10 are unchanged (a UUID4 `oid`, persisted, used by `==` and `hash`; versions are distinct atoms); only the assignment time changes. A new atom has no `oid` until first need - the first `oid` read, `==`/`hash`, or `_save` - when the UUID4 is generated under the atom's lock; once observed it never changes. A stub takes its `oid` from the payload on load (reading `oid` on a stub still loads it). The per-atom `RLock` is replaced by a module-level pool of 64 `threading.RLock`s; `_lock_for(atom)` picks one from `id(atom)` with the low four bits dropped and two bit ranges folded (plain `id % 64` hit only two stripes because object addresses are aligned). Lock order rule: a thread holding an atom stripe never acquires another atom stripe; re-acquiring its own stripe is allowed. To make that hold, `_save` encodes its state (which saves the children) with no stripe held and takes its stripe only to publish its own payload (check pointer, assign `oid`, push, set pointer); `_load` fetches the payload once under the stripe and keeps it on the stub, decodes it with no stripe held (decoding may hash, and therefore load, child stubs), and publishes the first decoded state under the stripe with the loaded flag set last. Storage locks are leaves: they are taken under a stripe but never call back into atoms. `_state` iterates a copy of the instance dictionary because another thread may add the lazily assigned `oid` concurrently.
- Alternatives: keep eager UUIDs (rejected: half the construction cost for identities most nodes never need); a cheaper identifier such as a process counter (rejected: changes the persisted format and global uniqueness); striped locks held across children saves and payload decoding, relying on re-entrancy (rejected: two unrelated atoms sharing a stripe give an A-B/B-A deadlock between a parent and a child on crossed stripes); per-atom locks created lazily for stubs and on first save (unnecessary once no stripe is nested).
- Consequences: a `PosNode` costs about 1.5 us to build (was 4.2 us) and a 10^4-element `pos_insert` sequence runs in about 0.29 s (was 0.69 s). The UUID cost moves to the first save or comparison: saving a freshly built 10^4-node tree is about 35 % slower (135 ms vs 101 ms), about break-even with the construction saving when every node built is saved, and loading costs about 10 % more (two stripe acquisitions per stub). Concurrent first saves of one atom may encode its state more than once; only one payload is pushed. A stub fetch holds its stripe during the storage read, so a slow read can briefly delay unrelated atoms on the same stripe. `values.is_atom` reads `oid` and therefore assigns it.

## D22 - IndexedCollection, IndexSet and net-effect replay details
- Context: spec section 8.1 and rulings R5/R6 fix the API (`IndexedCollection`, `IndexSet`, `as_query_plan`, `rebase_onto`) but not how new versions are built, what an op log contains, how index-definition changes merge, or what a no-op mutator must return.
- Decision: `IndexSet` is an immutable atom over a keyed AVL tree (`name -> index`); its element hooks map every index through `with_added`/`with_removed`/`with_replaced` and reject a hook result whose `name` differs; an empty set returns itself. Collections and index sets refuse public attribute assignment after construction. A collection declares its persisted fields in `_fields` (must include `count` and `indexes`) and runtime fields to carry over in `_runtime_fields` (gathered across the MRO); `_with(**changes)` builds a new instance from them and rejects unknown names. `add_index` checks the name before building and builds `index.empty().build(elements())`, so content held by the passed index object never leaks into the collection (rebase replay uses the same path). `_with` rejects an `indexes` value that is not an `IndexSet`. `IndexedCollection.__contains__` defaults to an O(n) scan by `values_equal`; subclasses override it. `ConcurrentOptimized` keeps a runtime-only `_op_log` (never persisted; a loaded version starts empty); the log records intent, not observed change: every mutator call logs its op (add means present, remove means absent, set means mapped to that value), including blind writes that change nothing in the transaction's version; such a call returns a new version carrying the extended log and reusing the receiver's content and indexes (no index work). Mutators are idempotent with respect to their intent, so replay applies each net op unconditionally and every touched key ends in its last intended state. `rebase_onto(current)` replays the last op per key (`order_key(op[1])` by default) in order of last occurrence, unconditionally, through the subclass's `_replay_op`, then index-definition changes per name: created here -> added (`ProtoConflictError` if `current` already has that name), removed here -> removed if present, removed-then-added -> replaces `current`'s, created-then-removed -> nothing; added indexes are rebuilt over the merged elements. `ConcurrentOptimized` must precede `IndexedCollection` in the bases (checked at class creation). Query plans are runtime objects, not atoms; `Estimate(rows, cost)` is a frozen dataclass of finite non-negative floats in `query/plans.py`. In the collection contract a mutator whose expected events are empty may return the receiver or an equal new version; every other mutator must return a new object.
- Alternatives: replay index ops in log order (rejected: an index created and dropped within a transaction would conflict with, or delete, a concurrently created one); log only observed changes (rejected, controller ruling in the Task 3.2 review: a blind write that was a no-op on the snapshot would be dropped, giving merges that match no serial order, e.g. snapshot {k:1}, theirs k=2 and j=5, mine k=3 and remove j -> {k:3, j:5}); a shared empty `IndexSet` singleton (rejected: atoms bind to the first context that saves them).
- Consequences: every collection version saves its own (possibly empty) IndexSet atom once; mutators that do not change content cost no index work but still allocate a new version to carry the log. The collection contract checks `rebase_onto` for every ConcurrentOptimized factory against an independent intent model the factory supplies (`rebase_model`). Rebasing re-runs `build` for indexes added by the transaction.

## D23 - List, Dictionary and HashDictionary details
- Context: spec section 8.2 lists the APIs of `List`, `Dictionary` and `HashDictionary` but leaves open position conventions, error behaviour, how slices treat indexes, which of them merge concurrently, the HashDictionary node layout and key domain, and the bulk builders.
- Decision: `List` (`proto_db/collections/lists.py`, persisted `root`/`count`/`indexes`) uses Python position conventions: negative positions count from the end; `get_at`, `set_at`, `remove_at` and `insert_at` raise `ProtoValidationError` for an out-of-range, `bool` or non-`int` position (0.1 returned `None`, indistinguishable from a stored `None`); `slice(start, stop)`, `head(n)` (`slice(None, n)`) and `tail(n)` (`slice(n, None)`) clamp like Python slices and return a new collection whose indexes are the same definitions rebuilt with `empty().build` over the slice (they are derivations, not edits, so they are not registered as contract mutators). `extend` accepts any iterable, reads it fully first, fires one add event per item and returns the receiver for an empty iterable. `List` is NOT `ConcurrentOptimized`: positional ops have no per-key net effect, so a written `List` root is last-writer-wins (spec section 7 "other types"). `Dictionary` (`dictionaries.py`) is a `KeyNode` tree ordered by `order_key(key)`; keys must be orderable (`list`/`dict`/NaN keys raise `ProtoValidationError`), values are any canonical value; `get_at(key, default=None)`; replacing keeps the first key object. `HashDictionary` (`hash_dictionaries.py`) is a `KeyNode` tree keyed by the bucket hash (`values.hash_key`, D24) whose node value is a bucket: a tuple of `(key, value)` pairs compared by `values_equal`; its key domain is that of `hash_key`, i.e. the same as Dictionary's (lists and dicts are no more hashable than orderable); iteration is in bucket-hash order (deterministic per content, not part of the API). Both dictionaries are `ConcurrentOptimized` with ops `("set", key, value)` and `("remove", key)` replayed per key through `set_at`/`remove_at`; setting an existing key always fires `on_replace(old, new)`, even for an equal value. Bulk builders: `List.from_iterable(items, context=None)` (O(n)) and `Dictionary.from_items`/`HashDictionary.from_items(pairs, context=None)` (sort plus O(n) build; a later pair for an equal key wins its value, the first key object is kept). All values are passed through `values.canonical`.
- Alternatives: making `List` ConcurrentOptimized with positional replay (rejected: an insert at position i in two concurrent versions has no serial meaning once the positions shift); returning `None` for an out-of-range position; HashDictionary buckets as nested AVL trees (unnecessary: with a 64-bit hash buckets almost always hold one pair); accepting `list`/`dict` keys in HashDictionary by hashing their contents (rejected: mutable containers as keys, and inconsistent with `values_equal`).
- Consequences: concurrent writers of one `List` root must read it (conflict and retry) to avoid losing an update. A list or dict value read back from a collection is the stored object, so callers must not mutate it. Spec section 8.2's "equality by content" is not implemented as `__eq__`: collections are atoms and `==` stays identity by `oid` (D10), consistent with `order_key` of atoms; content comparison is done by iterating.

## D24 - Process-stable hash_key
- Context: `values.hash_key` was `hash(order_key(value))`. Python salts the hash of `str`, `bytes` and date/time objects per process (`PYTHONHASHSEED`), so a structure ordered by `hash_key` and persisted (HashDictionary buckets now, Set and EqualityIndex later) would be unreadable after a restart: lookups would compute different bucket hashes than the stored tree order.
- Decision: `hash_key(value)` is the signed 64-bit BLAKE2b digest of an unambiguous encoding of `order_key(value)`: the rank byte, then for numbers their exact rational value modulo the Mersenne prime 2**61-1 (computed from `as_integer_ratio` for floats and from digits and exponent for `Decimal`, with modular exponentiation so `Decimal("1E+999999999")` is cheap; infinities get their own tags), length-prefixed UTF-8 (`surrogatepass`) for `str`, length-prefixed bytes, integer encodings for the other payloads (microseconds for datetimes, times and timedeltas, ordinal for dates, `int` for UUIDs and atom oids), and a count-prefixed recursive encoding for tuples. It stays consistent with `values_equal` (`1`, `1.0` and `Decimal(1)` hash alike; `True` does not).
- Alternatives: Python's `hash` with a fixed `PYTHONHASHSEED` (rejected: a process-wide setting a library cannot impose); keeping `hash` for in-memory use and adding a second persistent hash (rejected: two hashes consistent with the same equality invite using the wrong one in a persisted structure).
- Consequences: `hash_key` costs about 1.5 us for a scalar and 3.7 us for a 2-tuple on 3.14t (one BLAKE2b call plus the encoding) instead of a builtin hash; its values are part of the persisted format: changing the encoding requires a format migration.

## D25 - Frozen list and dict values (ruling R13)
- Context: `values.canonical` copied lists and dicts on the way in but stored plain mutable containers. `Dictionary.get_at("k")` returned the stored dict, so mutating it silently changed the published version for every reader and desynchronised indexes built from the old content.
- Decision: `values.FrozenList(list)` and `values.FrozenDict(dict)` are the only list and dict forms stored. `canonical()` returns them recursively (including containers nested in tuples) and is idempotent: input already canonical is returned as the same object. Codec decode produces them recursively; encode accepts frozen and plain. Every mutator (`append, extend, insert, pop, remove, clear, sort, reverse, __setitem__, __delitem__, __iadd__, __imul__, update, setdefault, popitem, __ior__`) raises `ProtoValidationError` telling the user to call `.copy()` first. `.copy()` returns a plain mutable shallow `list`/`dict` (nested values stay frozen). `copy.copy`, `copy.deepcopy` and pickle return an equal frozen container. Equality with plain containers holds (`FrozenList([1]) == [1]`); both stay unhashable for `hash()`, and `hash_key`/`order_key`/`values_equal` are unchanged. Contents are filled in `__new__`, so `__init__` is a no-op and cannot mutate.
- Alternatives: copy-on-read (rejected: an O(size) cost on every read); documenting "do not mutate" (rejected: it was the bug); read-only `MappingProxyType`/tuple (rejected: breaks `isinstance(x, list|dict)` and equality expectations).
- Consequences: C-level callers that bypass method dispatch (`list.append(frozen, x)`, `dict.__setitem__`) can still mutate; this guards against accidents, not against deliberate bypass. `tests/support/exact.py` treats a frozen container as the same kind as its plain counterpart.

## D26 - Set, CountedSet and RepeatedKeysDictionary details; counter merge by composed transform
- Context: spec section 8.2 names the APIs of `Set`, `CountedSet` and `RepeatedKeysDictionary` but leaves open their structure, what `elements()` yields for multisets, which index events counts imply, what the set algebra does to indexes and op logs, and how counters merge concurrently. Spec names `count(e)`/`total` clash with the persisted `count` field (number of elements, required by `IndexedCollection`) and with the atom rule that a persisted attribute may not shadow a class attribute.
- Decision: `Set` and `CountedSet` (`proto_db/collections/sets.py`) are built like `HashDictionary` (D23): a `KeyNode` tree keyed by `hash_key` (D24) whose node values are bucket tuples, membership by `order_key` equality (`values_equal`); a shared private base `_HashBuckets` holds the lookup, and `_bucket_hash` stays an overridable pure function (the same collision-test seam as `HashDictionary`). Elements are canonical and must be orderable; `True` and `1` are distinct, `1`, `1.0` and `Decimal(1)` are one element (first object kept); atom elements are identified by oid, so a reloaded stub is the same member. `Set` buckets hold elements; API `add`, `remove` (absent: content no-op, logged), `has`/`in`, `elements`, `union`/`intersection`/`difference` (any iterable operand; a fold of `add`/`remove`, so indexes are maintained incrementally, the receiver is untouched and the log records per-element intent: union logs an add per operand element, difference a remove per operand element, intersection a remove per own member absent from the operand), `Set.from_iterable`. Merge: last intent per element (`net_effect`). `CountedSet` buckets hold `(element, count)` with `count >= 1`; persisted `count` = distinct elements, `total_count` = sum of counts (both plain attributes); API `add` (increment), `remove` (decrement; deleting at 1; absent is a no-op), `count_of(e)`, `items()` (element, count), `has`, `elements()` = each distinct element once, `CountedSet.from_iterable`. Index events: `on_add` only when an element first appears, `on_remove` only when its count reaches zero; increments and decrements in between fire nothing. Counter merge (refines the brief's "net delta"): `ConcurrentOptimized` gains the hook `_net_ops(element_ops)` (default `net_effect`); `CountedSet` composes its ops per element into the transform `c -> max(c - removes, 0) + adds` (an add increments `adds`; a remove consumes a pending add, else increments `removes`) and applies it on the current version as ONE adjustment per element (`final = max(c - removes, 0) + adds`; amended in review fix round 1, replacing `removes` decrements then `adds` increments), logged as `("transform", e, removes, adds)` (RKD: `("transform_record", key, record, removes, adds)`), which `counter_net_effect` composes like any other op, so a merged version can itself be rebased. A surviving element therefore sees no remove/add index churn and replay costs O(log n) per element, not per unit. This equals replaying the transaction's ops one by one after the concurrent version, so two concurrent increments both count; it equals "current + (adds - removes), clamped at 0" whenever no remove of the log hit zero, and differs exactly when it did (mine: remove, remove, add on a count of 1 leaves 1; plain net delta would leave 0, which no serial order produces). `RepeatedKeysDictionary` (`dictionaries.py`) is a `KeyNode` tree ordered by `order_key(key)` (Dictionary key rules) whose values are non-empty `CountedSet`s of records without indexes or op logs; persisted `root`, `count` (distinct `(key, record)` pairs = number of elements), `total_count` (all occurrences), `indexes`. API `set_at(key, record)` (one more occurrence), `remove_record(key, record)` (one fewer; other records of the key kept; the key goes with its last record), `remove_at(key)` (all records), `get_at(key)` (the CountedSet, or an empty one), `has`, `keys`, `items` ((key, CountedSet)), `from_items`, and the spec 8.2 names `add`, `remove_key`, `get` as aliases. `elements()` yields each distinct record of each key once, in key order (consistent with CountedSet); events: `on_add(record)` when a record first appears under a key, `on_remove(record)` when its last occurrence under that key goes, one `on_remove` per distinct record on `remove_at`. Merge per key: if the log removed the key, replay `remove_at` and then the counter transforms of the record ops after the last `remove_key` (ops before it are absorbed by the clear); otherwise replay the transforms only. Ops: Set/CountedSet `("add", e)`/`("remove", e)`; RKD `("add", key, record)`, `("remove_record", key, record)`, `("remove_key", key)`.
- Alternatives: last-op-wins for counters (rejected: two concurrent increments would merge to one, losing an update for the most common counter use); plain net delta `adds - removes` clamped at zero (rejected: not equivalent to any serial order when a remove of the log found nothing); rebuilding indexes with `empty().build` in the set algebra (rejected: O(n) per operation regardless of the operand size and the derived set would lose per-element intent in its op log); `elements()` yielding every occurrence of a CountedSet (rejected: an index would hold n copies of an element and every increment would be an index event); building `Set` on a `HashDictionary` instance (rejected: a second atom per version and value slots carrying nothing).
- Consequences: the spec 8.2 names `count(e)` and `total` are `count_of(e)` and `total_count` (confirmed by the controller). `RepeatedKeysDictionary.remove_record` validates the record (orderable) before logging, even for an absent key, so a log never holds an op that replay would reject. The set algebra always returns a new version, as `add`/`remove` do. A record stored under two keys is two elements, so an index sees it twice (as Dictionary values). RKD records must be orderable (they are CountedSet members). Each RKD key holds one CountedSet atom plus its (empty) IndexSet atom when saved.

## D27 - content_equals (ruling R12)
- Context: ruling R12 keeps `==` as oid identity for collections (D10) and asks for an explicit content comparison.
- Decision: `IndexedCollection.content_equals(other) -> bool` returns False when `type(other) is not type(self)` (exact type; any non-collection gives False), True for the same object, False when `count` differs, and otherwise delegates to the hook `_same_content(other)` (called only with the same type and count). Indexes and op logs are not content. Values compare with `base.same_value`: `values_equal` for orderable values, recursive comparison for lists, dicts and tuples (a list never equals a tuple), NaN equals NaN (a stored NaN is the same content), atoms by oid. The default hook compares `elements()` pairwise in order (List). Overrides: Dictionary compares `(key, value)` pairs in key order; HashDictionary, Set and CountedSet look every entry up in `other` (their iteration order depends on collision-bucket insertion order, so it is not content); CountedSet also compares `total_count` and per-element counts; RepeatedKeysDictionary compares keys in order and each key's CountedSet with `content_equals`.
- Alternatives: a hook returning comparable "content items" (the review's suggestion `_content_items()`; rejected in favour of a comparison hook because the order-independent collections compare by lookup in O(n log n) without materialising and sorting); `__eq__` by content (rejected by R12).
- Consequences: comparing two loaded versions loads both trees fully. A nested collection held as a value (other than RKD's CountedSets) compares by identity, like any atom.

## D28 - Minimal term model and scan oracle
- Context: Task 4.1 needs terms to define index support and the scan oracle every index must agree with, before Task 6.1 builds the expression layer; spec section 10 says only "Term(path, op, value) ... evaluation uses values.py semantics".
- Decision: `proto_db/query/terms.py` defines the frozen dataclass `Term(path, op, value)` and the operator constants with the 0.1 spellings: `EQ "=="`, `NE "!="`, `LT "<"`, `LE "<="`, `GT ">"`, `GE ">="`, `IN "in"`, `BETWEEN "between[]"` (both bounds included), `BETWEEN_EXCL_BOTH "between()"`, `BETWEEN_EXCL_LOW "between(]"`, `BETWEEN_EXCL_HIGH "between[)"`, `IS_NONE "?N"`, `NOT_NONE "?!N"`, `NEAR "near[]"`. `path` names a key as a `KeySpec` term path: a dotted path, `None` for the element itself, `"@name"` for a registered extractor (so a path segment may not start with `@`). Terms are validated on construction: scalar comparisons need one canonical orderable operand other than MISSING; `in` a list/tuple/set of such operands (stored as a tuple); the between variants a `(low, high)` pair of one type rank (stored as a tuple); `?N`/`?!N` no value; `near[]` values are left to the vector layer. `Term.matches(element)` semantics: `==`/`in` by `values_equal` (`1 == 1.0`, `True != 1`), `None` is an ordinary value; a MISSING key matches no comparison, `!=` included, and only `?N`; `?N` is true for MISSING and None, `?!N` for every other key; `!=` = present and not `==`; range operators and between variants only match keys of the operand's type rank (`None < 5` and `"a" > 1` are false), ordered by `order_key`; unorderable keys (list, dict, NaN) match only `?!N` and `!=`; `near[]` raises `ProtoNotSupportedError` (answered by vector plans). Fix round 1 (ruling R17 accepted these semantics): a `near[]` value is canonicalised into the frozen, hashable `NearQuery(vector, k=None, threshold=None, metric=None)` (a mapping of those fields is converted; anything else is rejected): `vector` a non-empty tuple of finite floats, `k` an int >= 1, `threshold` a finite float, at least one of `k`/`threshold`, `metric` one of `cosine`, `l2`, `ip` or None (the index's default). `Term.matches` keeps raising `ProtoNotSupportedError` for `near[]`: without a fixed metric and the whole collection (k nearest) there is no per-element scan semantics; the vector contract (Task 7.1) supplies an exact kNN oracle through `IndexContract.oracle`. `in` over a set or frozenset stores its operands sorted by `order_key`, so equal sets give equal (and equally hashed) terms; a list or tuple keeps the caller's order. Every term is hashable.
- Alternatives: cross-rank range comparisons under the global total order (rejected: `age < 30` would return every None and bool, surprising and contrary to the 0.1 behaviour); `!=` true for MISSING (rejected: absence is not a value, and `NOT_NONE` exists to ask for presence); new operator spellings (rejected: the 0.1 vocabulary is what users and LINQ already know).
- Consequences: a RangeIndex must restrict range scans to the operand's rank; an EqualityIndex answering `!=` must exclude MISSING. Task 6.1 extends this module (And/Or/Not, planner) without changing these semantics.

## D29 - Index framework base: KeySpec, Index hooks and defaults, IndexPlan, package name
- Context: spec section 8.3 lists the hooks; the brief and the controller's resolutions settle most of the shape but not persistence of key specs, the mechanics of `empty()`, the `build` semantics on a populated receiver, the default `validate`, nor the package name, which collides with the 0.1 module `proto_db/indexes.py` (a package `proto_db/indexes/` shadows it and breaks every 0.1 import, and ruling R4 forbids deleting 0.1 modules before Task 8.5).
- Decision: the framework lives in `proto_db/indexing/` (`keyspec.py`, `base.py`); ruling R16 makes `proto_db.indexing` the permanent package name (no rename at Task 8.5). The abstract base persists as `proto_db.indexing.Index`; every concrete Index subclass must set `__type_name__` in its own class body (`Index.__init_subclass__` raises `ProtoUserError` otherwise; abstract intermediate classes may rely on the default), so persisted indexes never depend on module paths. `proto_db.indexing` resolves `Index`/`element_identity` lazily (PEP 562) because `query.terms` depends on `indexing.keyspec` and `indexing.base` on `query.terms`. `KeySpec` is a frozen value `(kind, arg)` with kinds `path`, `element`, `extractor`, compared by value and persisted inside the index as the plain tuple `(kind, arg)` (the index's `_keyspec_fields` are converted in `_state`/`_restore`), not as a separate atom. Path extraction: each step reads a persisted attribute of a DBObject (`has_defined_attr`) or of another atom (its loaded public state, so methods are never read), or a key of a mapping; private and reserved names are never read from atoms; any absent step or step through another value yields MISSING; explicit None stays None. Extractors: a process-wide thread-safe registry, `register_extractor(name, fn)`; same function again is a no-op, another function under a registered name raises `ProtoValidationError` (persisted indexes rely on the name keeping its meaning); resolution happens at extraction, an unregistered name raises `ProtoValidationError` naming it; results pass through `canonical`. `Index(Atom, metaclass=ABCMeta)`: immutable public state; definition fields in `_definition` (at least `name`, `key_spec`, checked at class creation); abstract `with_added`, `with_removed`, `supports`, `estimate`, `plan`; helpers `_with(**changes)`, `_on_key(term)` (term names this key), `_check_supported(term)` (raises `ProtoNotSupportedError`). Defaults: `with_replaced` = remove then add; `empty()` = `type(self)(**definition, context=self.context)` (so `__init__` must build an empty index from the definition); `build(elements)` = fold of `with_added` starting from `self.empty()`, i.e. an index over exactly `elements`, whatever the receiver holds; `explain()` = `{"index", "kind", "key"}`; `validate(elements)` compares plan and scan result multisets (`element_identity`) for every supported term among `==` on each distinct orderable key, `?N` and `?!N`, raising `ProtoCorruptionError`. `IndexPlan(index, term, producer, *, kind="IndexLookup")` in `query/plans.py`: `producer()` returns a fresh iterator per `execute()`; `explain()` = `{"plan": kind, "index": index.explain(), "term": term.describe()}`; `estimate()` delegates to the index. Fix round 1: `estimate(term)` on an unsupported term raises `ProtoNotSupportedError`, like `plan` (checked by contract (e)). Ordered iteration (spec 8.3, used by `order_by`) is discovered on any index without `isinstance`: defaults `supports_order(key_spec) -> False` and `ordered_plan(descending=False)` raising `ProtoNotSupportedError`; an index that orders overrides both. `ordered_plan` yields every stored occurrence ascending by `order_key` of the extracted key, i.e. MISSING < None < bool < number < ... per the values total order, with unorderable keys (list, dict, NaN) after every orderable key; descending is the exact reverse of that key-group order; the order inside one key group is unspecified. The contract compares the output as a sequence of key groups, each group as a multiset. `IndexPlan` accepts `term=None` (ordered plans) with a required explicit `estimate=`, and `details=` entries added to `explain()`. Deviation: composite keys (the spec's "attribute path(s)") are not implemented in 2.0; a KeySpec names one path, the element or a named extractor (an extractor may return a tuple, which orders lexicographically).
- Alternatives: KeySpec as an atom (rejected: an extra stored atom per index and oid identity for what is a value); `plan` as a template method calling an abstract `_plan` (rejected: the hook names are fixed by the ruling; the contract verifies the raise instead); `build` folding onto the receiver (rejected by the controller: build must be safe on a populated index); naming the package `proto_db/indexes` (impossible under R4 without breaking the 0.1 graph and its canary suite; R16 then kept `indexing` for good); ordered iteration through an `isinstance` check on a RangeIndex class (rejected: the planner must discover the capability on any kind).
- Consequences: every index kind passes `tests/contracts/index_contract.py` (checks (a)-(h) plus hook equivalences and explain); `ScanIndex` and `OrderedScanIndex` (tests/support) are the trivially correct references, and ten deliberately broken variants are each rejected by the check aimed at their defect. The default `validate` cannot see stale entries whose key no live element has unless the index supports `?!N`; kinds should override `validate` with structural checks. Every task imports from `proto_db.indexing`.

## D30 - EqualityIndex and RangeIndex: structure, rank-bounded ranges, cost model
- Context: spec section 8.3 names the two kinds and their structures (EqualityIndex a HashDictionary `hash_key(key) -> CountedSet(elements)`, RangeIndex a keyed AVL `order_key(key) -> CountedSet(elements)`) but not how duplicates, MISSING, unorderable keys or unorderable elements are stored, how D28's same-rank range semantics are realised, nor the estimates the planner (Task 6.2) will compare. Rulings R10 (bulk build), R16 (package `proto_db.indexing`) and R18 (unorderable keys in a side bucket, last in ordered iteration) apply.
- Decision: both kinds share the abstract `KeyGroupIndex` (`proto_db/indexing/keyed.py`); `EqualityIndex` (`equality.py`, type name `proto_db.indexing.EqualityIndex`) and `RangeIndex` (`range.py`, `proto_db.indexing.RangeIndex`) differ only in `supports` and ordering. Constructor `(name, key_spec)`, where a `str` key spec means `KeySpec.path` (the parameter keeps the name `key_spec` because `empty()` rebuilds the definition by field name). Persisted fields: `groups`, a keyed AVL (`KeyNode`) ordered by `order_key` of the extracted key, MISSING and None being ordinary keys at the bottom; `side`, the group of elements whose key is unorderable (list, dict, NaN, tuple holding one); `total_count`. A group is the tuple `(members, odd, total)`: `members` a keyed AVL from each orderable element (atoms by oid) to its occurrence count, `odd` a keyed AVL from the surrogate of each unorderable element to `(element, count)`, `total` its occurrences. The surrogate (`keyed.surrogate`) is a tagged orderable encoding (`("l", items)`, `("d", sorted pairs)`, `("t", items)`, `("n",)`, `("v", value)`), injective up to value equality; it lives only in `odd` trees, so it cannot collide with a real element. Plain keyed AVLs replace the spec's HashDictionary and CountedSet: measured on 3.14t at 1e5 string keys, an `order_key` descent costs the same as a descent over integer hashes (about 6.5 us either way) while `hash_key` adds about 1.6 us per operation (BLAKE2b, D24) and collision buckets; a CountedSet per key would add a collection atom plus an IndexSet atom per key and hash every element. EqualityIndex therefore uses the same ordered tree; it does not offer ordered iteration (its contract is lookups only, leaving room for a different structure later). Operators: EqualityIndex `==`, `in`, `!=`, `?N`, `?!N`; RangeIndex those plus `<`, `<=`, `>`, `>=` and the four `between` variants; answers equal `Term.matches` (D28). Ranges are bounded to the operand's type rank by the new `values.rank_bounds(value) -> ((rank,), (rank + 1,))`, order keys that bracket exactly the keys of that rank, scanned with the new `avl.key_iter_okey_range` (order-key bounds; `key_iter_range` now delegates to it). `?!N` is the range above None plus the side group; `!=` walks every group above MISSING except the operand's, plus the side group. Ordered iteration (RangeIndex): groups ascending then the side group; descending is the exact reverse (side group first, via the new `avl.key_iter_reversed`), as the 4.1 contract requires; R18's "matched by EQ via values_equal" is moot because terms reject unorderable operands, so unorderable keys match only `!=` and `?!N`. `with_removed` of an element the index does not hold raises `ProtoValidationError` (a silent no-op would hide a collection bug). `build` groups elements in Python dicts keyed by order keys, sorts, and builds every tree with `key_from_sorted` (R10). `validate` is structural: AVL invariants of every tree, each element filed under its own key with a positive count, group and index totals consistent, and the stored multiset of `(key slot, element identity)` equal to the elements' (no leftovers, nothing missing or miscounted); since that determines every answer the default O(keys x n) plan-vs-scan comparison is not repeated.
- Cost model (units of `CollectionScanPlan`: one unit per element produced or touched; G = distinct orderable keys, d = log2(G + 2) tree levels): `==`, `in` (distinct operands m), `?N` (two lookups): rows exact from the group totals, cost = rows + m * d; range and `between`: keys in range k exact from subtree counts (`avl.key_count_below`, O(log G)), rows = k * (orderable occurrences / G) (an estimate: nodes count keys, not occurrences), cost = rows + d + k; `?!N`: rows exact, cost = rows + d + groups visited; `!=`: rows exact, cost = total_count + G + 1, i.e. a complement walk is charged a full pass plus its group visits, so a bare scan (cost = count) always wins and the index is chosen only when the planner adds a residual-filter cost to the scan (spec: "via complement estimate: scan preferred"); ordered plan: rows = total_count, cost = total_count + G + 1.
- Alternatives: the spec's HashDictionary + CountedSet (rejected for cost, above); storing unorderable elements in a linear tuple per group (rejected: a List of dict records indexed by a path would make every update O(group size)); keying members by `element_identity` (rejected: it contains frozensets, which are not storable values); occurrence-augmented nodes for exact range row counts (rejected: would need a third node kind in `avl.py` for an estimate); treating `!=` like `?!N` in the cost model (rejected by the spec's "scan preferred").
- Consequences: on 3.14t, build costs 10-13 us per element at 1e5 (records keyed by a 1,000-value path, or 1e5 distinct ints) against 58-75 us per element for the fold of `with_added`; one `with_added`/`with_removed` costs about 65 us at 1e5, dominated by path copying of two AVL paths (a single `key_put` on a 1e5 tree costs about 51 us). Persisted indexes are found by type name, so `proto_db.indexing.equality`/`.range` must be imported before a stored index is loaded (importing `proto_db.indexing.EqualityIndex` does it).
- Amendment (review fix round 1 of Tasks 4.2/4.3, controller ruling): equality of keys is not enough for returned values; a plan must return exactly the stored elements a scan returns (type, Decimal exponent, tzinfo). A group is now `(members, total)` with `members` a keyed AVL from a member key `(equality part, exact token)` to `(element, count)`: the equality part is `(0, element)` for an orderable element and `(1, surrogate(element))` otherwise (the separate `odd` tree is gone); `keyed.exact_token` encodes a type tag (qualified class name for subclasses) plus an exact payload (`float.hex`, `str` of Decimals, ISO form + fold + utcoffset + tzinfo `repr` for datetimes and times, items in order for tuples, lists and dicts; atoms `("a",)` since the equality part already holds the oid). Equal members are adjacent in the tree, so `with_removed` removes an exact match first and otherwise one occurrence of an equal member (O(log n) through order-key bounds). `validate` compares `(key slot, element_identity, exact_token)` multisets. Cost after this amendment (3.14t, 1e5): build 16-20 us per element (with the new `avl.key_from_sorted_okeys`, which reuses the builder's order keys), `with_added`/`with_removed` about 80-95 us in a quiet heap (noisy, up to about 150 us); the round-0 figures in the Consequences above predate exact member keys. The index contract gained `exact_key` (`exact_value_key` = type name and `repr`) for plain-value registrations, and the mixed strategy now draws equal-but-distinct values (`1`, `1.0`, `Decimal("1")`, `Decimal("1.00")`, `0.0`, `-0.0`, same-instant aware datetimes in several zones, dicts with the same items in another order). `ScanIndex`/`OrderedScanIndex` (test references built on CountedSet) keep equality-level fidelity and are not registered with `exact_key`.

## D31 - Built-in atom types resolve without a prior import
- Context: atoms are resolved by `__type_name__` through a registry filled when a class is defined, so a process that opens a stored database without importing, say, `proto_db.indexing.range` or `proto_db.collections.lists` failed with "Unknown atom type" (found in the Task 4.2/4.3 review; escalated by the controller).
- Decision: `proto_db/core/atom.py` holds `BUILTIN_ATOM_MODULES`, a fixed table from every built-in 2.0 atom type name (core, collections, indexing) to its defining module. On a registry miss `Atom._class_for` imports that module (outside the registry lock, since registration takes it) and retries; a name absent from both still raises `ProtoCorruptionError`. `tests/unit/test_atom_type_modules.py` imports every module of the 2.0 packages, walks all `Atom` subclasses and requires each built-in one to be in the table with its module (so the table cannot rot), and loads a Dictionary holding a List with an EqualityIndex and a RangeIndex from a FileStorage in a fresh interpreter that imports only `proto_db.storage` and `proto_db.core`.
- Alternatives: importing every built-in module eagerly from `proto_db.core` (rejected: import cycles and start-up cost); persisting module paths with each atom (rejected: type names are deliberately decoupled from module paths, D29).
- Consequences: user-defined atom classes still need their module imported before loading (unchanged); a new built-in atom class must be added to the table, or the table test fails.

## D32 - Space root layout and database history
- Context: spec section 7 names `ObjectSpace -> Database -> Transaction` but not what the storage root points to, how databases share one root, or how `Database.history()` finds older versions.
- Decision: the storage root points to a `SpaceRoot` atom (`proto_db.transactions.SpaceRoot`) whose `databases` field is a `Dictionary` name -> `DatabaseRoot`. A `DatabaseRoot` (`proto_db.transactions.DatabaseRoot`) holds `objects` (a `Dictionary` root name -> value: any canonical value or atom), `version` (0 at creation, +1 per commit), `committed_at` (aware UTC, never decreasing along the chain: `max(now, previous.committed_at)`) and `previous` (the replaced `DatabaseRoot`, `None` for version 0). Both types are in `BUILTIN_ATOM_MODULES`. `Database.history()` walks `previous` and returns `HistoryEntry(version, committed_at, root_names)` newest first, with `root_names` loaded on access. All databases of a space share one storage root and epoch; conflicts are decided per root name, so commits to different databases never conflict with each other (they only serialize on the root lock).
- Alternatives: one storage root per database (rejected: the storage contract has a single root, and cross-database atomicity would be lost); no history link (rejected: `history()` is part of the API); history in a separate list atom (rejected: an extra atom rewrite per commit for nothing).
- Consequences: every commit writes a new `DatabaseRoot`, a new `SpaceRoot` and the O(log n) path of both dictionaries; old versions are kept forever (no compaction yet), since each `DatabaseRoot` references its predecessor.

## D33 - Merge only values whose op log is complete
- Context: D9 merges roots written but not read by replaying the written value's op log (`rebase_onto`). The F0 blind-write test requires the merge even when the root did not change since the snapshot (snapshot `{a:10, b:5}`, blind write of a new dictionary `{c:3}` must commit `{a:10, b:5, c:3}`), so the rule cannot be "merge only if changed concurrently". But a ConcurrentOptimized value whose content is not described by its log (loaded, bulk-built with `from_items`/`from_iterable`, or rebased) would lose that content when replayed: `tr.set_root_object("b", tr.get_root_object("a"))` would silently leave `b` unchanged.
- Decision: `ConcurrentOptimized` keeps a runtime-only flag, `log_is_complete`: true for a collection constructed empty (`__init__`) and for versions derived from it through `_with` calls that extend the log whenever they change persisted content; false for loaded stubs (class default), bulk-built versions, rebased versions and everything derived from them. At commit, a root written but not read is stored as `written.rebase_onto(current)` iff the written value is ConcurrentOptimized with a complete log and the current root holds a value of the same type (changed since the snapshot or not); otherwise the written value replaces the current one (last writer wins). The original written version is always the one rebased.
- Alternatives: merge only when the current value differs from the snapshot (rejected: the F0 blind write would replace the whole dictionary); always merge unread ConcurrentOptimized roots (rejected: silent loss of content not covered by the log); compare `rebase_onto(empty)` with the value at commit (rejected: O(n) per commit and ambiguous).
- Amendment (Task 5.1 review fix round 1, controller ruling; the maintainer confirmed that replay applies to every unread root): `set_root_object(name, value, *, replace=False)`; `replace=True` stores the value as written (last writer wins, no merge), and so does a set that follows `remove_root_object(name)` in the same transaction. Once a name is marked for replacement it stays so for the rest of the transaction. The `set_root_object` docstring states that a fresh collection written to an existing unread root is merged into it, not substituted. After a successful publish the transaction marks every written ConcurrentOptimized value's log as incomplete (its intent has been consumed), so a value held and reused in a later transaction replaces instead of replaying the earlier transaction's ops again; a failed commit leaves the values mergeable.
- Consequences: blind writes have intent semantics independently of concurrency; assigning a loaded or bulk-built collection to an unread root is a replacement. Reading back, within the transaction, a root written before it was read returns the value as written, not the merged one.

## D34 - Commit protocol, unknown publish outcomes and transaction threading
- Context: spec sections 6-7 fix the read set, the root lock and "nothing can fail after publish", but not the order of saves and checks, what a failed `publish_root` with an unknown outcome means for the transaction (D19), or the threading contract of a transaction.
- Decision: commit = (1) no writes: nothing saved or published; (2) save written values, children first, outside the root lock (append-only storage); (3) `root_lock(space.lock_timeout)`, timeout raises; (4) read the current root; if its epoch differs from the snapshot's, compare every read-set entry (an exact token, or ABSENT) with the current root, any difference raising `ProtoConflictError`; (5) merge per D33 (`ProtoConflictError` from `rebase_onto` propagates), build and save the new `DatabaseRoot`/`SpaceRoot`; (6) `storage.flush()` then `publish_root(ptr, expected_epoch)`. When publishing raises a ProtoDB error or `OSError`, the root is read back: our pointer visible means the commit succeeded (logged); another epoch means `ProtoConflictError`; otherwise the original error is raised (an `OSError` wrapped in `ProtoUnexpectedError`); if the root cannot be read back, `ProtoUnexpectedError` reports an unknown outcome. (7) After a successful publish only best-effort steps remain (releasing the root lock, marking the written logs consumed per D33); their ProtoDB or OS errors are logged, never raised. On the failure path a lock-release error is logged as well, so it never masks the original conflict or publish error. `SharedStorage.root_lock` documents that releasing may raise only ProtoDB errors or `OSError`; no broad handler is used. Any failed commit leaves the transaction aborted; every public method of an ended transaction raises `ProtoUserError`. `Database.run` retries only `ProtoConflictError`, `retries` times after the first attempt, sleeping `d * uniform(0.5, 1)` with `d = min(max, min * 2**attempt)`. A transaction is single-threaded by contract but not bound to a thread: an internal lock serializes its operations, so a misuse from several threads cannot corrupt it. Its `save`/`load` (PersistenceContext) keep working after it ends, because atoms it created or loaded may outlive it; `save` refuses atoms bound to another storage (`ProtoUserError`).
- Read-set tokens (amended in Task 5.1 review fix round 1, controller ruling): `proto_db.values.exact_token(value, atom_token)` (moved from `indexing/keyed.py`, which re-exports it) with atoms, nested ones included, tokenised by storage pointer. Plain values compare by type and exact payload: `1` vs `1.0`, `Decimal("1")` vs `Decimal("1.00")`, `0.0` vs `-0.0`, and one instant in two time zones are all changes, hence conflicts for a reader.
- Alternatives: `same_value` for plain values (rejected in review: a concurrent `1 -> 1.0` rewrite went unnoticed by a reader); comparing atoms by oid in the read set (rejected: loads the stubs; pointers identify a saved version exactly); raising on use from another thread (rejected: handing a transaction to a worker thread is legitimate); failing the commit whenever `publish_root` raises (rejected: reports a failure for a commit that is visible).
- Consequences: only an exactly identical rewrite of a plain root (same type and payload) by a concurrent commit is not a conflict for a reader of that root; a storage that raises after making the root visible still yields a successful commit, and a file storage disabled by the failure must be reopened for later commits (D19).
